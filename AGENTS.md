# AGENTS.md

This file is the guidance for coding agents and new contributors working in this repository.

## Commands

Access the environment through `pixi`. The `test39` and `test315` environments carry the
test and dev tooling (pytest, ruff, ty) on Python 3.9 and 3.15; `doc` carries sphinx;
`cupy` is defined for `linux-aarch64` (the Jetson), `linux-64`, and `win-64`, not macOS:

```sh
pixi run -e test39 pytest                                        # full suite, py39
pixi run -e test315 pytest                                       # full suite, py315
pixi run -e test39 pytest tests/waveform/test_waveform_fourier_stft.py -q   # one file
pixi run -e test39 pytest -k test_stft_linearity                 # one test by name
pixi run -e test39 ruff format src tests                         # format (single quotes, 88 cols)
pixi run -e test39 ruff check src tests
pixi run -e test315 ty check src                                  # type check (must pass on test39 and test315)
pixi run -e test315 pyright src                                   # advisory; accepted count in Conventions → Typing
pixi run -e test315 pyrefly check                                 # advisory; accepted count in Conventions → Typing
pixi run -e doc sphinx-build -E -a -b html doc doc/html          # docs (see chores/push-docs.sh to deploy)
pixi run -e cupy pytest                                          # GPU path, Jetson only
STRIQT_CACHE_DIR=$(mktemp -d) pixi run -e cupy python tests/profiling/pipeline_sync.py --buffers 2  # own disk caches
```

The on-disk cache (the `persistent_cache` window shelf) lives in
the platformdirs user cache directory unless `STRIQT_CACHE_DIR` names another one. Two
striqt processes that share the window shelf corrupt it on macOS Python 3.9, so a script
run beside a test session or another script sets its own directory. The test suite does
this itself.

Every pixi environment installs the conda-forge `soapysdr` package (the `null` driver
only) and striqt as an editable PyPI dependency with its `dev` extra; `pixi run` refreshes
that install when `pyproject.toml` changes. `pytest` is 8.x on py39 and 9.x on py315, and
only pytest 9 reads the `[tool.pytest]` table in `pyproject.toml`, so test configuration
that must hold on both goes in `tests/conftest.py`. `uv run --extra test|dev|doc` still
works as a fallback but is not the project's environment.

Adding `--frozen` to `pixi run` skips the manifest/lock-file consistency check, saving
the reinstall (and any network fetch) that a `pyproject.toml`/`pixi.toml` edit would
otherwise trigger — but it also means a newly added dependency silently isn't installed,
surfacing as an `ImportError` instead of pixi's normal "lock file not up-to-date" message.
Default to running without it; reach for `--frozen` only in a tight loop of commands
where the manifest is already known not to have moved.

SoapySDR tests come in three tiers: pure units and tests against the fake `SoapySDR` module in `tests/sensor/fake_soapy.py` run everywhere; `TestNullDriver` needs the real bindings, which every pixi environment has; tests marked `hardware` need an attached Airstack and are skipped unless `STRIQT_TEST_HARDWARE=1 pixi run -e cupy pytest -m hardware` opts in on the Jetson.

`tests/sensor/` runs one canonical synthetic sweep YAML (`tests/sensor/sweeps/synthetic.yaml`) and the site-style sweeps under `tests/sensor/sweeps/site/` end to end through the CLI, writing to `tmp_path`; everything else builds specs programmatically from `tests/sensor/synthetic_sources.py` (capture presets, `acquire_corrected`, `run_in_memory` with a `NoSink`) and checks the corrected IQ against the `striqt.analysis.testing` generators.

## Architecture

Four packages under `src/striqt/`, stacked bottom-up: `striqt.waveform` → `striqt.analysis` → `striqt.sensor` → `striqt.figures`. Each depends only on those below it. Public API lives in each package's top level (`striqt.analysis`, `striqt.sensor`, …). Everything under `.lib` is internal and changes without warning.

The architecture guide is in `doc/agents/`, written primarily for ingest by coding agents. Read the page for an area before changing code in that area:

- `doc/agents/architecture.md`: package layout and the re-export shims, spec structs as the YAML/JSON/zarr schema, and the measurement registry (caches, `prefer_filtered`/`prefer_aligned`, signal triggers, the `BuiltinAnalyses` group).
- `doc/agents/waveform_numerics.md`: numpy/cupy dispatch, the Fourier package, STFT layout, resampling, the window cache, and the OFDM and 5G NR synchronization models.
- `doc/agents/sensor.md`: sensor bindings, actions and runners (sweep, Y-factor calibration, cellular sweep), extensions and the downstream project, sweep execution and the per-capture signal path, and logging and concurrency.

### Known gaps are recorded as strict xfails

Library defects that need a design decision rather than a local fix are written as `pytest.mark.xfail(strict=True, reason=...)` tests against the intended behavior, so `grep -rn "xfail" tests` lists them with their causes. Read the reason before treating a red test as new, and expect a genuine fix to turn that xfail into an unexpected pass that must then be removed. The ledger `tests/xfail-audit.md` records each one (see the xfail ledger in `tests/AGENTS.md`).

## Conventions

- **Lint.** `pixi run -e test39 ruff check src tests` reports nothing. The rule set is ruff's default plus preview, with the architectural exclusions and the reason for each in `[tool.ruff.lint] ignore` in `pyproject.toml`; `pyupgrade.keep-runtime-typing` keeps `Union`/`Optional` for msgspec. A line that must keep a flagged pattern carries `# noqa: <RULE>` with the reason, never a bare `# noqa`. Three import orders are pinned with `# isort: split`/`# isort: off` because the sorted order breaks an import cycle or ty inference; keep the comment beside each. Fix with `ruff check --fix-only --fixable <RULES>` under the full config rather than `--select`, which redefines the enabled set and makes RUF100 report every other `noqa` as unused.
- **Python 3.9 is the floor** (`requires-python = ">=3.9"`, ruff `target-version = "py39"`; the `test39` and `test315` pixi environments cover both ends). Modules start with `from __future__ import annotations as __` so annotations can use modern syntax, but anything evaluated at runtime cannot.
- **msgspec resolves struct annotations at runtime.** In spec structs use `Union[...]`/`Optional[...]`, not `X | None`, and keep the names importable at runtime. `eval_type_backport` is a hard dependency for this reason. Several recent commits are reverts of "simplifications" here — collapsing a `Union`, or rewriting a `Literal` containing bools, has broken msgspec decoding before. Run the tests in `tests/sensor/` after touching a spec type.
- **Lazy imports are enforced.** Heavy modules are loaded via `util.lazy_import('scipy')` under an `if TYPE_CHECKING:`/`else:` split. `tests/test_imports.py` asserts that `scipy`, `xarray`, and `pandas` are still unreified and that `dask` was never imported after importing all four packages. Adding a module-level `import xarray` in the wrong place fails that test.
- **Test layout.** One test module per source module, named `test_<package>_<module>.py` (`tests/sensor/test_sensor_specs_sequencing.py` covers `sensor/specs/sequencing.py`, `tests/sensor/test_sensor_actions_core.py` covers `sensor/lib/actions/core.py`), with `# %%` cells per function or class under test; add new tests to the existing module rather than creating a file per feature. `tests/` has no packages: module basenames must be unique across all subdirectories, and shared helpers are imported by bare name (`from conftest import ...`, `from sweep_strategies import ...`) because pytest's prepend import mode puts each test directory on `sys.path`. Do not add a `conftest.py` below `tests/` — pytest drops `sys.modules['conftest']` before loading each one, so a nested conftest would be what `tests/waveform/*` get from `from conftest import ...`. Put fixtures in the root conftest and strategies in one plainly named module per package (`tests/analysis/analysis_strategies.py`, `tests/sensor/sweep_strategies.py`), with the backend-agnostic primitives (`scalars`, `bounded_ints`, `finite_floats`, `short_text`) in the root conftest beside the array strategies. The root conftest also loads the hypothesis profile (function-scoped fixtures allowed, no deadline), so property tests need no `@settings` unless they set `max_examples`; cupy-dependent tests take the `cupy_available` fixture, and tests that should run on both backends take the parametrized `xp` fixture.
- **Array-namespace agnostic numerics.** Use `sw.array_namespace(x)` to get the namespace and dispatch; don't hard-code `numpy`. Everything must work on numpy and cupy, in 32-bit float.
- For functions that need to return structured data based on named fields, prefer use of `dataclasses` or `msgspec.Struct` over `typing.TypedDict` or named tuples
- **Functions over methods.** On `msgspec.Struct`, `dataclasses`, and `SpecBase` objects, new and refactored behavior is a module-level function that takes the object, not a method, following the Python custom around dataclasses (`specs.action.validate_sweep(sweep)`, `actions.yfactor.calibration_passes(spec)`, `actions.cellular.ssb_symbol_indexes(channel)`); write a method only when explicitly instructed, or when polymorphic dispatch on the class is the point (`ActionSpec.check_schema`, the `__post_init__` chain). In other classes, a helper that reads only a few `SpecBase` objects and plain Python values is a module-level function taking them as arguments, not a method on `self`.
- **Typing.** Every new or edited function, method and closure carries hints for all parameters and the return; only `self`/`cls` and lambdas are exempt. Wrapper catch-alls are `*args: P.args, **kwargs: P.kwargs`. Reuse the aliases in `striqt.waveform.lib.typing` (`Array`, `ArrayLike`, `XpType`, `ArrayBackend`, `WindowType`, `DTypeLike`, `LRUWrapped`), `striqt.analysis.lib.typing` (`Measurement`, `AnalysisFunc`, `WrappedAnalysis`, `CoordFunc`, `ZarrStore`) and `striqt.sensor.lib.typing` (`PS`/`PC`, `ResamplerKws`, `PassThroughWrapper`); `xp` is `ModuleType` when required and `XpType` when `None` means "infer"; `dtype` is `DTypeLike`. A decorator that returns a wrapper names its type variables in the return annotation (`-> CoordFuncWrapper[TC, TM, R]`, not the bare alias), otherwise ty erases the wrapped signature to `Unknown`.
  - `**kwargs` forwarded to a fixed target are `**kwargs: Unpack[<Name>Kws]` with the `TypedDict` defined in that package's `lib/typing.py` (`ResamplerKws` is the model); anything else is `**kwargs: Any`. `TypedDict` is for keyword sets only; structured return values stay `dataclasses`/`msgspec.Struct`. ty 0.0.81 does not flag unknown keywords through `Unpack` (strict xfail in `tests/test_typing.py`).
  - Measurement signatures are typed through `@hint_keywords(spec_type)`; a measurement body is `(x: Array, capture: specs.Capture, **kwargs: Any) -> Measurement`. `tests/test_typing.py` runs ty over probes generated from `sa.registry` and asserts that every registered measurement exposes its spec fields statically, and over hand-written probes for the other keyword-unpacking sites.
  - `pixi run -e test315 ty check src` and `pixi run -e test39 ty check src` must both report no diagnostics; ty applies the 3.9 rules in both (`[tool.ty.environment]` in `pyproject.toml`). The two environments carry different dependency stubs (zarr 2, IPython 8, matplotlib 3.9, and pandas 2 on test39), so a name that exists in one version only is reached through a module bound to `typing.Any` (`storage: typing.Any = importlib.import_module('zarr.storage')`) rather than through an ignore comment, which the other environment reports as unused. `tests/test_typing.py` enforces the test315 gate.
  - Suppress with `# ty: ignore[rule-name]` on the offending line, never a blanket `# ty: ignore` or `# type: ignore`. An ignore that is unused in one environment is a warning there, so on version-gated branches (zarr 2/3) suppress only what the test315 stubs reject.
  - pyright and pyrefly run in advisory mode, pinned to 3.9 like ty (`[tool.pyright]`, `[tool.pyrefly]` in `pyproject.toml`). Their remaining diagnostics are checker gaps, not hint problems: pyright 53 errors and pyrefly 40 errors on `src/` as of 2026-09-24 (numpy stubs without `normalize_axis_tuple`, the zarr 2/3 `hasattr` gate, `dict`-subclass `__hash__`, optional `cupy` imports, `TypeIs` to uninstalled torch/cupy, msgspec runtime-valued annotations in bound sweeps, deliberate protocol deviations, the `for k in list(locals())… del k` re-export loops, and a few flagged defects). Do not add `# pyright: ignore` or `# pyrefly: ignore` comments (ty never honored them and they hide more than they explain): fix a new diagnostic with a better hint, or leave it in that count. Write `Union`/`Optional` rather than `X | Y` inside the `TYPE_CHECKING` alias blocks of the `lib/typing.py` modules, since pyright evaluates those under 3.9.
- **Comments:** only write one if a competent engineer or agent reading the code cold would be surprised or misled without it. Worth writing: a non-obvious *why* (constraint, workaround, domain rule, performance trade-off); something that looks wrong but is intentional; external context that can't be inferred from the code (section from a technical standard, peer-reviewed publication, government report, public documentation, upstream bug/issue number); an invariant or precondition the types don't enforce. Do not write:
  - changelog or progress notes (`# added null check`, `# refactored from previous version`) — the diff is already in git. Progress notes belong in the chat response, the commit message, or the PR description, never in a source file comment;
  - narration of the obvious (`# loop over captures`, `# return the result`);
  - restatements of the signature or type annotations;
  - conversational leakage (`# as requested`, `# per the instructions`, `# TODO: user said to`);
  - section banners, unless the file is genuinely huge. Note that the existing `# %% Capture specs` markers are Jupyter-style cell delimiters, not decoration.

  If a comment is needed to explain *what* code does, prefer renaming or extracting a function instead — that removes the cause rather than the symptom. Comments are for *why*. A comment is prose and follows the procedure under **Prose in code** below.

  After editing, re-read every comment you added and delete any that restate the code or describe the change rather than the code. This pass is cheap and catches most stragglers. The pass covers the comments in code the task has changed, not every comment read along the way; a wider comment sweep requires an explicit request or authorization from the user.

- **Docstrings** are the API reference (sphinx autodoc + napoleon render them into `doc/`), so write them as the caller's contract: inputs, outputs, side effects, exceptions. Google sections only — `Args:`, `Returns:`, `Yields:`, `Raises:`, `Examples:`, `References:` — never `Arguments:`, numpy underlines, or ad hoc headers.
  - **Drafting order.** Write the summary line first, then the `Args:`/`Returns:`/`Raises:` entries from the signature, then one sentence per remaining fact, each starting with its subject. Run the **Check** list under **Prose in code** on each docstring before moving to the next function, not once at the end of the change.
  - **This object's contract only.** A docstring states what the object requires, returns, raises, and changes. It does not say what other code does with the object: not where a function is registered, which caller invokes a method, or when another class reads an attribute ("registered as the `on_cached` callback", "`iterate_sweep` calls `iterate`", "a bound spec reads `sweep` at the end of `__post_init__`"). A hook may name its intended consumer in one clause of the hook's own docstring ("the sink that `open_resources` enters") and no more.
  - **Log messages.** A docstring names the logger and the level a function logs on, and the condition that produces a record. Never the text of a message, in full or in part.
  - **Sections before prose.** A fact about one parameter is that parameter's `Args:` entry. A fact about the return value is the `Returns:` entry. Prose above the sections carries only facts that span several parameters or the object's state. Three sentences that each name one parameter are an `Args:` block written in the wrong place. A sentence that restates an `Args:` entry, or that points the reader to another object's docstring ("whose docstring describes the yields"), is deleted: the docstring stands on its own, and autodoc links the names in backticks.
  - **Args state the contract.** An `Args:` entry says how the value selects, constrains, or shapes the output ("the open resources", "`None` disables the filter", "one value per port, in dB"). It does not say what the body does with the value ("the implementation invokes ...", "the calibration path and the source id are read"). A behavior the body applies to one argument is a prose sentence when this function owns the behavior, and one prose sentence naming the owning function when another function does ("An implementation runs `iterate_captures` over `resources`."). That cross-reference replaces detail; a pointer that stands in for a claim this docstring must make itself is still deleted. An entry is one brief clause, at most 2; detail beyond that goes in the prose above the sections, not in the entry.
  - **Summary line.** One line, imperative mood, lowercase first word, naming the effect or the returned quantity with its units: "return the duration (in s) of one 3GPP slot at `subcarrier_spacing`". Not "an iterator that ...", "helper for ...", "this function ...", or a third-person verb ("designs ..."). Include a trailing period unless the docstring
  is one-line docstring. `pixi run -e test39 ruff check --select D401 src` lists non-imperative summaries; it is not enforced, so run it on files you touch. One claim per summary line: a trailing participial clause carries a second claim and is cut (", yielding what the sink's `append` returns" becomes a `Yields:` entry; ", raising what the builder raises" a `Raises:` entry). "run the action over `resources`." is a whole summary.
  - **Module docstrings.** Do not catalog the module's contents or repeat details of the objects in its namespace; autodoc renders those from the objects' own docstrings. Give the context a reader needs before any one object: the theme of the module, and an implementation fact that applies across it and is written in no comment. Use the restraint of the Comments guidance. No return types, signatures, or naming patterns of the members (`describe_*`); no statement of what the module does not do ("nothing here logs"); no reference to the program that consumes the output.
  - **Class docstrings.** State what an instance is and the contract shared by every method (what construction requires, state the methods share, a lifecycle such as a context manager), in at most 3 sentences. Every fact about one method, property, or field goes in that member's docstring; autodoc renders those. For a `Protocol`, the class docstring states the role an implementation plays and nothing about registration, callers, or inheritance. Dataclass fields take an attribute docstring (below); spec-struct fields are documented through `Meta`, and the spec class docstring says how the fields interact. Construction requirements and effects go in the `__init__` docstring ("store `spec`; nothing is opened or derived."), and each public attribute takes an attribute docstring; the class docstring keeps what an instance is. `doc/conf.py` sets `napoleon_include_init_with_doc = True` so an `__init__` docstring renders.
  - **Dataclass fields.** Each field of a dataclass carries an attribute docstring: a string literal on the line after the field, one noun phrase with units and range (`snr_dB: float` followed by `"""peak SNR (dB) above the calibrated noise power"""`). Sphinx autodoc renders the literal as the member description. Do not also write an `Attributes:` section: with `undoc-members` on, napoleon's `.. attribute::` entries duplicate autodoc's member list. The rules for `Args:` entries apply to each attribute docstring, and the rules for sections versus prose apply to the fields versus the class docstring (**Sections before prose**, **Args state the contract**). An attribute docstring states the contract of the value: what the field selects, constrains, or shapes, and what `None`, `inf`, or `'auto'` selects. A fact about one field is that field's attribute docstring, never a sentence in the class docstring; the class docstring carries only facts that span several fields or the state and lifecycle of the instance. A class docstring sentence that names one field is an attribute docstring written in the wrong place.
  - **Predicate nouns.** In every "X of Y" and "Y's X", Y is the thing that has X. "The IM3 victims of a port" fails: the products belong to the signal of the capture at that port, and the victims are the frequencies those products fall on. Rewrite until each possessive names the actual owner.
  - **Language** Write with American english and spelling.
  - **State what the signature cannot.** An `Args:` entry adds meaning, never type: units (Hz, s, S/s, dB vs linear power), array shape and which axis holds what, dtype, valid range or ratio constraint, and what `None`/`inf`/`'auto'` selects. `x: input array` and `fs: sampling rate` are omissions, not entries. `Returns:` gives shape, axis layout or dimension names, dict keys, units, and whether the array namespace follows the input. Generators use `Yields:` and say what ends the iteration (`loop=True` is infinite).
  - **Side effects are contract.** In-place modification (`overwrite_x`, `out=`, including an `out=` that is accepted but not honored), process-global state (logger handlers, caches, the GPU lock), threads started, files written.
  - **`Raises:`** lists every exception the caller can act on with its condition. Omit exceptions that only a bug would raise. An entry names the exception type and the condition that produces it; it does not reproduce the message string of the exception, in full or in part.
  - **Avoid repeating exact code in the function when documenting the return value**. Rather, state which inputs will be used to compute the returned value, and the scope
  of possible return values such as bounds, etc.
  - **Behavior, not mechanism.** Name the method only when it decides the result or the cost (overlap-add edge behavior, the copy made by `_truncated_buffer`, a disk-cached window design). No step-by-step narration of the body; when the steps *are* the observable precedence (`loop_captures`), state them as rules.
  - **Constraints, not their reasons.** State what the caller must satisfy and what they get back. The reason a constraint exists belongs in a code comment at the line that enforces it, if anywhere; never in the docstring.
  - **Present tense, present code.** Nothing about what the code used to do, was changed to do, or may do later — no "now", "no longer", "previously", "new", "legacy", "used to", "fix", "workaround", "TODO", "for now". Hedges, person and the lexicon are under **Prose in code** below. Code that converts older data describes the condition it finds ("`units` of the form `dBm/<bandwidth>`"), not the version or era that wrote it ("stores written before X carried Y").
  - **Cite external context.** A standard section, a paper, or an upstream issue is cited in its short form inline, in parentheses ("(3GPP TS 38.211 §5.3.1)", "(Gardner 1986)"). The long form of each citation (full title, authors or standards body, year, URL or DOI) goes under a `References:` section at the end of the docstring, one entry per source.
  - **Do not duplicate what the tooling injects.** Spec-struct fields are documented through `Meta(description=..., units)`; the class docstring says what the block configures and how its fields interact, never a field list. A measurement docstring ends with `Args:\n    {args}`, which the registry fills from the `Meta` field metadata of `spec_type`, so every field is already documented there; the prose above repeats none of that content. Read the field metadata first to find the context the prose still has to supply: the output values (dtype, units, normalization), how the fields interact, and the conditioning the measurement registers. `Controller` subclass and `arm` docstrings are generated.
  - **Measurement docstrings.** A function decorated with `@registry.measurement` carries an `Output:` section between the prose and the remaining sections, written as this bullet list with the placeholders verbatim (`doc/conf.py` registers `Output` as a napoleon section, and the registry fills `{dtype}`, `{dims}`, `{coords}`, and `{attrs}` at registration):

    ```
        Output:
            - Array dtype: {dtype}
            - Dimensions: {dims}
            - Coordinates: {coords}
            - Attributes: {attrs}
              * `noise_bandwidth`: the bandwidth (in Hz) that the values are referred to
    ```

    `{dtype}` renders as the registered dtype name. `{dims}` renders as the backticked dimension names of the returned `DataArray`, `port` first. `{coords}` renders a nested list with one ``* `name` (dtype, units): description`` item per entry of `coord_factories`, from the registration and the docstring of the factory; a measurement registered without coordinate factories omits the `Coordinates` bullet. `{attrs}` renders a nested list of the registered attrs other than `standard_name` and `long_name` (`units`, when registered). The attrs that the measurement body returns (`units` when the body sets it, `noise_bandwidth`, `resolution_bandwidth`) are hand-written items on the lines after `{attrs}`, indented 2 spaces under the `-`, one ``* `key`: value`` item per attr, with units and the fields the value comes from; a `units` item states only that the power units follow the acquisition and what the unit is when calibrated ("power units based on acquisition (dBm when calibrated)"). A measurement with no registered `units` and no body attrs omits the `Attributes` bullet. Section order is prose, `Output:`, `Raises:`, `References:`, then `Args:` with `{args}` last. The prose above the sections names no dimension, no coordinate, and no attr: a fact about one coordinate is the docstring of that coordinate factory, a fact about one attr is an `Attributes` item, and the prose repeats nothing the list renders (dtype, dimensions, units, the attrs). A fact about the values that the list does not render (normalization, `nan` entries, what a bin collects) stays in the prose.
  - **Coordinate factory docstrings.** The docstring of a function decorated with `@registry.coordinates` is the attribute docstring of the coordinate, not a description of the factory: one noun phrase stating what the values index, with the origin, step, span, and the fields that set them (`"""time from the start of the capture, in steps of \`detector_period\`"""`). The registry renders the first paragraph as the coordinate entry in every `{coords}` list that includes the factory, after the registered dtype and units, so the phrase repeats neither. Further paragraphs (a `Returns:` for the attrs the factory returns) are not rendered in `{coords}`. A factory without a docstring renders as its `standard_name`; `tests/analysis/test_analysis_register.py` requires a docstring on every registered factory. These docstrings are the one exception to the imperative summary line, so ruff `D401` flags them by design.
  - **Markup.** Identifiers in single backticks (they render italic: no `default_role`), literal code in double backticks, examples in doctest form (ruff formats them with `docstring-code-format`).
  - **Length follows audience.** Public API (`striqt.analysis`, `striqt.sensor`, the `waveform` shims) gets full sections; a private `.lib` helper gets a summary line plus only the sections that carry information. No docstring beats one that restates the name.
  - **Scope of a change.** Bring the docstring of any function you edit to this standard, including stale parameter names and exception lists. Do not rewrite docstrings of untouched functions in the same change. A revision pass over docstrings or comments covers only the code the task has changed, never code read along the way; a wider pass requires an explicit request or authorization from the user.
  - **A noisy docstring is worse than none.** A docstring that narrates mechanism, names a `.lib` module, or describes the change that produced it costs review and maintenance time and returns nothing. When a refactor touches a documented object, delete the sentences that referenced the old mechanism; do not rewrite them. Add a sentence only when it states a caller-facing rule: what a value selects, what is rejected, which input a derived value comes from. A summary line alone is a complete docstring.
  - **Prose changes stay visible.** A docstring rewrite goes in a commit whose message names it, never inside one titled for a rename or refactor. The final chat message of a change lists every docstring touched, by qualified name, so the list can be reviewed without the diff.
  - **Gate.** `tests/test_docstrings.py` fails on any docstring under `src/` that contains a `striqt.<pkg>.lib` path outside a `lib/` directory, or one of "we", "our", "you", "your", "they", "their", "them", or "whose" outside backticks and doctest lines ("I" and "us" are not scanned: "I/Q" and the microsecond abbreviation). The scan has no baseline: every docstring under `src/` must pass.

  After editing, run 4 structural checks on every docstring you touched, before the **Check** under **Prose in code**; each is one rule of that section applied to a docstring, and the word scan does not replace them:
  1. (`agent`) Strike every sentence whose subject is a module, a table, a check, a runner, or the design. What remains must still state the caller's contract; if it does not, cut the docstring to the summary line.
  2. (`noun`) For every "it" and "its", the antecedent is the subject of the previous sentence and in the same noun category (field, block, measurement, parameter); otherwise write the noun. At most one "it" per paragraph.
  3. (`verb-first`) Cut each sentence after its first verb. If the claim is not yet stated, split the sentence or delete it.
  4. (`attach`) No sentence or clause ends in a preposition. "the `Sweep` that the resources open for" becomes "the `Sweep` for which the hardware is opened", or the sentence is turned around so the object comes last.

  Then delete any sentence that restates the signature, describes the change rather than the code, or hedges, and any clause that starts with "because", "since" or "so that" or sits in parentheses explaining the mechanism.

- **Prose in code reads like an engineer's, not a model's.** These rules apply to every comment, docstring, commit message, PR description, and prose file written into the repository; the habits they name pass ruff and still mark text as machine-written. The test for a sentence is whether a reader with the technical background, but without this session's context, comes away with the fact intact. The canonical shape is `Subject Verb Object [, qualifier]`: Subject is a thing that can literally do Verb, Verb arrives within about eight words with nothing between it and Subject, and everything after the first comma is a qualifier (units, rounding, condition) or a clause joined by the word that names its relation. The procedure below is the test for each of seven rules; name the rule id when a change report lists a prose edit. (`voice.md` "Sentence rules" in the `kuester-writing` skill is the manuscript form; a paper's voice allows "we", "In order to", "the following", "This is important:", "various", and "etc.", and code prose does not.)
  - **Procedure.** Run on every sentence written or edited, including one proposed by a reviewer, an agent, or a search-and-replace; re-run steps 1–3 on any sentence a split creates. (1) `noun`: name what each noun denotes; substitute the antecedent for every "it". (2) `agent`: can the subject, as the thing it names, do this verb to this object? If not, R1 or R2. (3) `verb-first` and `attach`: cut the sentence after its first finite verb; is the claim stated, is anything between subject and verb, does every modifier have one head beside it? If not, R3. (4) `join`: count the independent clauses; a bare comma, a semicolon beside a conjunction, more than three, or a colon in place of a connective: R4 or R5. (5) `verdict` and `compare`: delete each adjective, opener, and filler in turn; if no number, baseline, or condition is lost it stays deleted, and if one is implied, write it (R6); a comparison names baseline, quantity, amount, and condition (R7). (6) Words: the table at the end.
  - **Recipes.** R1 invert to the quantity: "<quantity> is limited by / set by / determined by <cause>". R2 demote the device to a condition: "With <device>, <quantity> fell within <value>". R3 move the fronted qualifier, the appositive, or ", not Y," after the main clause or into its own sentence, and make the relation verb the main verb. R4 split: one condition with its consequence per sentence, or one list item per rule. R5 replace the colon with "because", "so", "which means", or a period. R6 delete the word, or write the number, condition, or fact it stood for. R7 "Compared to <baseline>, <quantity> changes by <amount> under <condition>."
  - **`noun`: every noun denotes a thing in the code or the field, or a claim on the page.** Write the name (a key in backticks, once per sentence), the condition, or the clause. Not "the attr is set" but "the `noise_bandwidth` attr is set to `subcarrier_spacing`". Shapes: *during* a span (segment, read, capture), *at* a point (sample, index, strobe edge), *in* a container (buffer, chunk, queue); a retry resumes *with* or restarts *from* a segment; a value is set *on* an attribute and read *from* a field; "referred to" takes a reference plane, temperature, or impedance. A thing is named once and the noun reused: no "this pipeline", "this chain", "this logic", "the machinery". A placeholder for a condition the text never states ("this behavior", "edge cases", "the result", "the logic", "various", "etc.", "as expected", "the right thing", "what it does", "the present context") is replaced by the condition. Keep: "it" and "its" once per paragraph when the antecedent is the subject of the previous sentence and in the same noun category; otherwise repeat the noun.
  - **`agent`: the subject's class fixes the verbs it may take.** Replace the subject by what it literally is (a function, a number, an array, a key, a design, a page of text) before asking whether it can do the verb; fail, pass, and meet take a requirement as object, not an artifact. Fix: R1 for a cause or technique, R2 for a device, the fact it stands for when the subject is a design or the text itself. Not "the lock earns its place in the hot loop" but "the lock serializes GPU access from the acquisition and analysis threads". A pronoun keeps the class of its antecedent ("the estimate ... it assumes a reference": a number cannot assume; write "the estimator").

    | Subject class | May take | May not take |
    |---|---|---|
    | Code object: function, class, thread, controller, sink, caller | implements, follows, requires, returns, raises, reads, writes, allocates, serializes, holds <the store> open | handle, take care of, inherit, suffer from, struggle with, unlock, live in, do anything gracefully; "owns" (name what holds, allocates, or reads) |
    | Quantity or value: level, power, estimate, count | is, equals, averages, exceeds, is bounded by, is limited / set / determined by <cause> | sit, land, hover, read, see, report (a level); return, assume, decide |
    | Array, buffer, port, store, file, capture, waveform | its function with the object that verb takes (a buffer holds samples, a port carries a stream) | hold, carry, keep, achieve, reach, deliver a result; fail or meet an artifact |
    | Metadata key, attr, field, coordinate name | object of set, read, copy, remove, equal | take, gain, lose, carry, record, spell out; "the attr" alone without its key |
    | Design, contract, invariant, intent, approach, fix, correctness | is, requires <of the caller>, holds <for a range> | carry, anchor, earn, buy, pay for, hold up, stand, grow, feed, drive, turn into; a designer's decision (should maximize, choose, avoid) |
    | Abstract cause, choice, or technique: ripple, caching, "choosing N" | after "by" or in a because-clause; a change verb only with the amount or condition in the same clause | sets, limits, moves, offers, drives, improves, costs; the bare change verb ("caching increases the latency") |
    | The text about the code: this module, this docstring, the table, the check, the runner | nothing; strike the sentence, and what remains must still state the caller's contract | any verb |
  - **`verb-first`: subject, finite relation verb, object; qualifiers trail.** The verb after the cut must state the relation (fails, requires, exceeds, removes). Rewrite if an appositive or ", not Y," stands between subject and verb ("the estimator, a weighted correlator, returns"), if a qualifier precedes the subject ("rounded to one sample, the lag is the estimate" becomes "the estimate is the lag, rounded to one sample"), if the claim sits in a trailing relative clause ("renders one as the line that ``sensor-sweep`` logs"), or if a light verb plus abstract noun announces a verb that comes later ("has a requirement that ..."). Not a fix: moving the verb to a second clause on a pronoun that points back ("..., but coarse alignment fails it too"). Keep: a connective opener ("Thus,", "Further,", "First,") or a condition of about eight words or fewer ("With `loop=True`, ...").
  - **`attach`: one head per modifier, and next to it.** A participle, relative clause, "to <verb>", or prepositional phrase has one word it can modify and sits beside it; rewrite if two candidates exist, if a comma-bracketed clause separates it from its head, or if it narrates an event with its own time ("the capture analyzed when the cache filled"). Fix: name the thing ("the capture under analysis") and give the event, if the reader needs it, a sentence of its own; a purpose infinitive follows its verb directly. Keep: a participle that states a property ("the gated estimate").
  - **`join`: what a comma, a semicolon, and a colon may join.** An independent clause is a finite verb with its own subject outside any that/which/when/because clause; more than three, or clauses that could be reordered without changing the argument, are a list. Replace each colon or semicolon with a period: if the second sentence then needs "because", "so", "but", or "for example", write that word or keep the period. A colon announces a specification, list, or restatement. A semicolon does not append a critique to a description. A docstring that applies several rules states each as "condition: what is set", one list item per rule, with no numbered narrative and no appositive after the consequence.
  - **`verdict`: no grade, filler, or opener without its number.** For a verb of change or degree, ask by how much or under what condition. Not written: grades on the code or its design ("proper", "genuine", "real", "true", "clean", "cheap" as a judgement, "circular", "one-sided"); antitheses in place of the condition ("data, not assertions", "behavior rather than mechanism" as a slogan, "The problem is the cache."); evaluative openers and aphorisms ("This is important", "X is a solved problem", "the key insight is", "X has a cost:", "the trade-off is", "the catch is"); praise adjectives (robust, powerful, elegant, seamless, crucial, critical, comprehensive, clean, efficient, flexible, convenient, graceful, novel); performance boasts ("with speed optimizations"). "robust" takes an object ("robust to a DC offset") or is not written; a boast becomes the cost or nothing.
  - **`compare`: a comparison is a clause with a named baseline.** Rewrite if the baseline, quantity, amount, or condition is missing, or if the baseline trails the number as ", compared with <value>". Fix: R7 ("0.6x the numexpr time in float32 on the TX2i"), or the comparison is not made.
  - **Words not written.** Replace by the condition, the number, the task, or nothing. Time and change words ("now", "previously", "legacy", "fix", "TODO") are under **Present tense, present code** above.

    | Group | Not written | Write instead |
    |---|---|---|
    | Person and narration | "I", "we", "our", "us", "you", "your", "let's"; "they", "their", "them" for a variable, attribute, capture, template, or quantity; "whose"; "first we ... then we ..."; "the following"; "this will"; a sentence addressed to a reader or writer ("you are editing", "once you commit") | the noun; "the captures with gain above" for "the captures whose gain exceeds"; a list for a sequence (`tests/test_docstrings.py` gates the pronouns and "whose" in `src/`) |
    | Hedges and fillers | "should" where "must" is meant, "try to", "attempt", "safely", "properly", "simply", "just", "basically", "essentially", "effectively", "note that", "it is worth noting", "make sure", "sanity check", "for convenience", "under the hood" | the condition or the requirement |
    | Connective openers | "Additionally,", "Moreover,", "Furthermore,", "Importantly,", "In other words", "In order to" | "Further,", "Thus,"; the infinitive after its verb |
    | Lexicon | "utilize", "towards", "in practice", "trivial", "crucial", "vital", "very" as praise, "ground truth" outside quotation marks | "use", "toward", the condition, "straightforward", "key", the number |
    | Idioms and effort estimates | "an afternoon's work", "low-hanging fruit", "should go", "a leftover", "earns its place", "going forward", "at the end of the day", "in the other direction" | the task, the deletion, or the number |
  - **Commit messages.** The summary line is one imperative clause of about 72 characters or fewer that names the effect of the change ("Wait for the source backend before the sink reads its power units"), with no trailing period and no tag prefix; a summary that names no effect ("cleanup", "tweaks", "misc fixes", "updates") is not written. The body, when the summary does not carry the whole fact, states the condition the change addresses and what the code does after it, in the present tense of the new code ("`lookup.power_units` waits on the id slot"), one fact per sentence, and follows the procedure. Not written: "this commit", "now", "also", a list of the files touched, a progress note, or a sentence about the session or the reviewer. A docstring or prose rewrite is its own commit, named as such (**Prose changes stay visible**). The `Co-Authored-By` trailer stays as the tooling writes it.
  - **Mechanics.** Digits for counts ("3 statistics", "2 ports"); the Oxford comma; "e.g.," and "i.e.," with the trailing comma.
  - **Check.** After editing, run the procedure on every comment, docstring, and commit message you touched, in addition to the re-read passes under **Comments** and **Docstrings**. Delete or rewrite what fails. A sentence proposed by a reviewer, an agent, or a search-and-replace is new prose: run the procedure on each one in place before accepting it. A rewrite applied from a list is how the habits above return.
