# AGENTS.md

This file is the guidance for coding agents and new contributors working in this repository.

## Commands

Access the environment through `pixi`. The `test39` and `test315` environments carry the
test and dev tooling (pytest, ruff, ty) on Python 3.9 and 3.15, and `test315` also carries
zensical with the mkdocstrings and mkdocs-click handlers;
`cupy` is defined for `linux-aarch64` (the Jetson), `linux-64`, and `win-64`, not macOS:

```sh
pixi run -e test39 pytest                                        # full suite, py39
pixi run -e test315 pytest                                       # full suite, py315
pixi run -e test39 pytest tests/waveform/test_waveform_fourier_stft.py -q   # one file
pixi run -e test39 pytest -k test_stft_linearity                 # one test by name
pixi run -e test39 ruff format src tests docs                    # format (single quotes, 88 cols)
pixi run -e test39 ruff check src tests docs
pixi run -e test315 ty check src                                  # type check (must pass on test39 and test315)
pixi run -e test315 pyright src                                   # advisory; accepted count in Conventions → Typing
pixi run -e test315 pyrefly check                                 # advisory; accepted count in Conventions → Typing
pixi run -e test315 docs                                          # API pages, then the zensical site into site/ (chores/push-docs.sh deploys)
pixi run -e test315 docs-api                                      # regenerate docs/api/**/*.md from the public namespaces
pixi run -e test315 docs-serve                                    # zensical preview on localhost:8000
pixi run -e cupy pytest                                          # GPU path, Jetson only
STRIQT_CACHE_DIR=$(mktemp -d) pixi run -e cupy python tests/profiling/pipeline_sync.py --buffers 2  # own disk caches
```

The on-disk cache (the `persistent_cache` window shelf) lives in
the platformdirs user cache directory unless `STRIQT_CACHE_DIR` names another one. Two
striqt processes that share the window shelf corrupt it on macOS Python 3.9, so a script
run beside a test session or another script sets its own directory. The test suite does
this itself.

Every pixi environment installs the conda-forge `soapysdr` package (the `null` driver
only) and striqt as an editable PyPI dependency with its `dev` extra; `pixi run` refreshes
that install when `pyproject.toml` changes. `pytest` is 8.x on py39 and 9.x on py315, and
only pytest 9 reads the `[tool.pytest]` table in `pyproject.toml`, so test configuration
that must hold on both goes in `tests/conftest.py`. `uv run --extra test|dev|doc` still
works as a fallback but is not the project's environment.

Adding `--frozen` to `pixi run` skips the manifest/lock-file consistency check, saving
the reinstall (and any network fetch) that a `pyproject.toml`/`pixi.toml` edit would
otherwise trigger — but it also means a newly added dependency silently isn't installed,
surfacing as an `ImportError` instead of pixi's normal "lock file not up-to-date" message.
Default to running without it; reach for `--frozen` only in a tight loop of commands
where the manifest is already known not to have moved.

SoapySDR tests come in three tiers: pure units and tests against the fake `SoapySDR` module in `tests/sensor/fake_soapy.py` run everywhere; `TestNullDriver` needs the real bindings, which every pixi environment has; tests marked `hardware` need an attached Airstack and are skipped unless `STRIQT_TEST_HARDWARE=1 pixi run -e cupy pytest -m hardware` opts in on the Jetson.

`tests/sensor/` runs one canonical synthetic sweep YAML (`tests/sensor/sweeps/synthetic.yaml`) and the site-style sweeps under `tests/sensor/sweeps/site/` end to end through the CLI, writing to `tmp_path`; everything else builds specs programmatically from `tests/sensor/synthetic_sources.py` (capture presets, `acquire_corrected`, `run_in_memory` with a `NoSink`) and checks the corrected IQ against the `striqt.analysis.testing` generators.

## Architecture

Four packages under `src/striqt/`, stacked bottom-up: `striqt.waveform` → `striqt.analysis` → `striqt.sensor` → `striqt.figures`. Each depends only on those below it. Public API lives in each package's top level (`striqt.analysis`, `striqt.sensor`, …). Everything under `.lib` is internal and changes without warning.

The architecture guide is in `docs/agents/`, written primarily for ingest by coding agents. Read the page for an area before changing code in that area:

- `docs/agents/architecture.md`: package layout and the re-export shims, spec structs as the YAML/JSON/zarr schema, and the measurement registry (caches, `prefer_filtered`/`prefer_aligned`, signal triggers, the `BuiltinAnalyses` group).
- `docs/agents/waveform_numerics.md`: numpy/cupy dispatch, the Fourier package, STFT layout, resampling, the window cache, and the OFDM and 5G NR synchronization models.
- `docs/agents/sensor.md`: sensor bindings, actions and runners (sweep, Y-factor calibration, cellular sweep), extensions and the downstream project, sweep execution and the per-capture signal path, and logging and concurrency.

### Known gaps are recorded as strict xfails

Library defects that need a design decision rather than a local fix are written as `pytest.mark.xfail(strict=True, reason=...)` tests against the intended behavior, so `grep -rn "xfail" tests` lists them with their causes. Read the reason before treating a red test as new, and expect a genuine fix to turn that xfail into an unexpected pass that must then be removed. The ledger `tests/xfail-audit.md` records each one (see the xfail ledger in `tests/AGENTS.md`).

## Conventions

- **Lint.** `pixi run -e test39 ruff check src tests docs` reports nothing. The rule set is ruff's default plus preview, with the architectural exclusions and the reason for each in `[tool.ruff.lint] ignore` in `pyproject.toml`; `pyupgrade.keep-runtime-typing` keeps `Union`/`Optional` for msgspec. A line that must keep a flagged pattern carries `# noqa: <RULE>` with the reason, never a bare `# noqa`. Three import orders are pinned with `# isort: split`/`# isort: off` because the sorted order breaks an import cycle or ty inference; keep the comment beside each. Fix with `ruff check --fix-only --fixable <RULES>` under the full config rather than `--select`, which redefines the enabled set and makes RUF100 report every other `noqa` as unused.
- **Python 3.9 is the floor** (`requires-python = ">=3.9"`, ruff `target-version = "py39"`; the `test39` and `test315` pixi environments cover both ends). Modules start with `from __future__ import annotations as __` so annotations can use modern syntax, but anything evaluated at runtime cannot.
- **msgspec resolves struct annotations at runtime.** In spec structs use `Union[...]`/`Optional[...]`, not `X | None`, and keep the names importable at runtime. `eval_type_backport` is a hard dependency for this reason. Several recent commits are reverts of "simplifications" here — collapsing a `Union`, or rewriting a `Literal` containing bools, has broken msgspec decoding before. Run the tests in `tests/sensor/` after touching a spec type.
- **Lazy imports are enforced.** Heavy modules are loaded via `util.lazy_import('scipy')` under an `if TYPE_CHECKING:`/`else:` split. `tests/test_imports.py` asserts that `scipy`, `xarray`, and `pandas` are still unreified and that `dask` was never imported after importing all four packages. Adding a module-level `import xarray` in the wrong place fails that test.
- **Test layout.** One test module per source module, named `test_<package>_<module>.py` (`tests/sensor/test_sensor_specs_sequencing.py` covers `sensor/specs/sequencing.py`, `tests/sensor/test_sensor_actions_core.py` covers `sensor/lib/actions/core.py`), with `# %%` cells per function or class under test; add new tests to the existing module rather than creating a file per feature. `tests/` has no packages: module basenames must be unique across all subdirectories, and shared helpers are imported by bare name (`from conftest import ...`, `from sweep_strategies import ...`) because pytest's prepend import mode puts each test directory on `sys.path`. Do not add a `conftest.py` below `tests/` — pytest drops `sys.modules['conftest']` before loading each one, so a nested conftest would be what `tests/waveform/*` get from `from conftest import ...`. Put fixtures in the root conftest and strategies in one plainly named module per package (`tests/analysis/analysis_strategies.py`, `tests/sensor/sweep_strategies.py`), with the backend-agnostic primitives (`scalars`, `bounded_ints`, `finite_floats`, `short_text`) in the root conftest beside the array strategies. The root conftest also loads the hypothesis profile (function-scoped fixtures allowed, no deadline), so property tests need no `@settings` unless they set `max_examples`; cupy-dependent tests take the `cupy_available` fixture, and tests that should run on both backends take the parametrized `xp` fixture.
- **Array-namespace agnostic numerics.** Use `sw.array_namespace(x)` to get the namespace and dispatch; don't hard-code `numpy`. Everything must work on numpy and cupy, in 32-bit float.
- For functions that need to return structured data based on named fields, prefer use of `dataclasses` or `msgspec.Struct` over `typing.TypedDict` or named tuples
- **Functions over methods.** On `msgspec.Struct`, `dataclasses`, and `SpecBase` objects, new and refactored behavior is a module-level function that takes the object, not a method, following the Python custom around dataclasses (`specs.action.validate_sweep(sweep)`, `actions.yfactor.calibration_passes(spec)`, `actions.cellular.ssb_symbol_indexes(channel)`); write a method only when explicitly instructed, or when polymorphic dispatch on the class is the point (`ActionSpec.check_schema`, the `__post_init__` chain). In other classes, a helper that reads only a few `SpecBase` objects and plain Python values is a module-level function taking them as arguments, not a method on `self`.
- **Typing.** Every new or edited function, method and closure carries hints for all parameters and the return; only `self`/`cls` and lambdas are exempt. Wrapper catch-alls are `*args: P.args, **kwargs: P.kwargs`. Reuse the aliases in `striqt.waveform.lib.typing` (`Array`, `ArrayLike`, `XpType`, `ArrayBackend`, `WindowType`, `DTypeLike`, `LRUWrapped`), `striqt.analysis.lib.typing` (`Measurement`, `AnalysisFunc`, `WrappedAnalysis`, `CoordFunc`, `ZarrStore`) and `striqt.sensor.lib.typing` (`PS`/`PC`, `ResamplerKws`, `PassThroughWrapper`); `xp` is `ModuleType` when required and `XpType` when `None` means "infer"; `dtype` is `DTypeLike`. A decorator that returns a wrapper names its type variables in the return annotation (`-> CoordFuncWrapper[TC, TM, R]`, not the bare alias), otherwise ty erases the wrapped signature to `Unknown`.
  - `**kwargs` forwarded to a fixed target are `**kwargs: Unpack[<Name>Kws]` with the `TypedDict` defined in that package's `lib/typing.py` (`ResamplerKws` is the model); anything else is `**kwargs: Any`. `TypedDict` is for keyword sets only; structured return values stay `dataclasses`/`msgspec.Struct`. ty 0.0.81 does not flag unknown keywords through `Unpack` (strict xfail in `tests/test_typing.py`).
  - Measurement signatures are typed through `@hint_keywords(spec_type)`; a measurement body is `(x: Array, capture: specs.Capture, **kwargs: Any) -> Measurement`. `tests/test_typing.py` runs ty over probes generated from `sa.registry` and asserts that every registered measurement exposes its spec fields statically, and over hand-written probes for the other keyword-unpacking sites.
  - `pixi run -e test315 ty check src` and `pixi run -e test39 ty check src` must both report no diagnostics; ty applies the 3.9 rules in both (`[tool.ty.environment]` in `pyproject.toml`). The two environments carry different dependency stubs (zarr 2, IPython 8, matplotlib 3.9, and pandas 2 on test39), so a name that exists in one version only is reached through a module bound to `typing.Any` (`storage: typing.Any = importlib.import_module('zarr.storage')`) rather than through an ignore comment, which the other environment reports as unused. `tests/test_typing.py` enforces the test315 gate.
  - Suppress with `# ty: ignore[rule-name]` on the offending line, never a blanket `# ty: ignore` or `# type: ignore`. An ignore that is unused in one environment is a warning there, so on version-gated branches (zarr 2/3) suppress only what the test315 stubs reject.
  - pyright and pyrefly run in advisory mode, pinned to 3.9 like ty (`[tool.pyright]`, `[tool.pyrefly]` in `pyproject.toml`). Their remaining diagnostics are checker gaps, not hint problems: pyright 53 errors and pyrefly 40 errors on `src/` as of 2026-09-24 (numpy stubs without `normalize_axis_tuple`, the zarr 2/3 `hasattr` gate, `dict`-subclass `__hash__`, optional `cupy` imports, `TypeIs` to uninstalled torch/cupy, msgspec runtime-valued annotations in bound sweeps, deliberate protocol deviations, the `for k in list(locals())… del k` re-export loops, and a few flagged defects). Do not add `# pyright: ignore` or `# pyrefly: ignore` comments (ty never honored them and they hide more than they explain): fix a new diagnostic with a better hint, or leave it in that count. Write `Union`/`Optional` rather than `X | Y` inside the `TYPE_CHECKING` alias blocks of the `lib/typing.py` modules, since pyright evaluates those under 3.9.
- **Prose in code reads like an engineer's, not a model's.** These rules apply to every comment, docstring, commit message, PR description, and prose file written into the repository. The test for a sentence is whether a reader with the technical background, but without this session's context, comes away with the fact intact. The canonical shape is `Subject Verb Object [, qualifier]`: Subject is a thing that can literally do Verb, Verb arrives within about eight words with nothing between it and Subject, and everything after the first comma is a qualifier (units, rounding, condition) or a clause joined by the word that names its relation. **Rules** names the 7 ways a sentence breaks that shape, with the id cited in change reports; **Not written** is the word table; **Check** is the one pass run after editing. (`voice.md` "Sentence rules" in the `kuester-writing` skill is the manuscript form; a paper's voice allows "we", "In order to", "the following", "This is important:", "various", and "etc.", and code prose does not.)
  - **Rules.** Each rule has an id, a test, a recipe, and a Keep.
    - **`noun`: every noun denotes a thing in the code or the field, or a claim on the page.** Test: name what each noun denotes, and substitute the antecedent for every "it". Not "the attr is set" but "the `noise_bandwidth` attr is set to `subcarrier_spacing`". Prepositions follow the shape of the noun: *during* a span (segment, read, capture), *at* a point (sample, index, strobe edge), *in* a container (buffer, chunk, queue); a retry resumes *with* or restarts *from* a segment; a value is set *on* an attribute and read *from* a field; "referred to" takes a reference plane, temperature, or impedance. A thing is named once and the noun reused; the placeholder nouns and renamings are in the table. Keep: "it" and "its" once per paragraph when the antecedent is the subject of the previous sentence and the same kind of thing.
    - **`agent`: the subject's class fixes the verbs it may take.** Test: replace the subject by what it literally is (a function, a number, an array, a key, a design, a page of text) and ask whether that thing can do the verb to this object; fail, pass, and meet take a requirement as object, not an artifact; a verb that reads as well with a person or a team as its subject (wins, prevails, falls back, decides) reports an outcome and hides the rule. Fix: R1 for a cause or technique, R2 for a device, R8 for an outcome verb, the fact it stands for when the subject is a design or the text itself. Not "the lock earns its place in the hot loop" but "the lock serializes GPU access from the acquisition and analysis threads"; not "a looped field wins over an adjustment" but "a field named in both the loop and an adjustment takes the loop value". A pronoun keeps the class of its antecedent ("the estimate ... it assumes a reference": a number cannot assume; write "the estimator").

      | Subject class | May take | May not take |
      |---|---|---|
      | Code object: function, class, thread, controller, sink, caller | implements, follows, requires, returns, raises, reads, writes, allocates, serializes, selects, replaces, starts, holds <the store> open, logs on <logger> at <LEVEL> when <condition> | handle, take care of, inherit, suffer from, struggle with, unlock, live in, do anything gracefully; "owns" (name what holds, allocates, or reads) |
      | Quantity or value: level, power, estimate, count | is, equals, averages, exceeds, is bounded by, is limited / set / determined by <cause>, takes <value> when <condition> | sit, land, hover, read, see, report (a level); return, assume, decide |
      | Array, buffer, port, store, file, capture, waveform | its function with the object that verb takes (a buffer holds samples, a port carries a stream) | hold, carry, keep, achieve, reach, deliver a result; fail or meet an artifact; win, lose, prevail over, beat |
      | Metadata key, attr, field, coordinate name | object of set, read, copy, remove, equal | take, gain, lose, carry, record, spell out; win, take precedence (write the condition and the value the key takes); "the attr" alone without its key |
      | Design, contract, invariant, intent, approach, fix, correctness | is, requires <of the caller>, holds <for a range> | carry, anchor, earn, buy, pay for, hold up, stand, grow, feed, drive, turn into; a designer's decision (should maximize, choose, avoid) |
      | Abstract cause, choice, or technique: ripple, caching, "choosing N" | after "by" or in a because-clause; a change verb only with the amount or condition in the same clause | sets, limits, moves, offers, drives, improves, costs; the bare change verb ("caching increases the latency") |
      | The text about the code: this module, this docstring, the table, the check, the runner | nothing; strike the sentence, and what remains must still state the caller's contract | any verb |
    - **`verb-first`: subject, finite relation verb, object; qualifiers trail.** Test: cut the sentence after its first finite verb; the remainder states the relation (fails, requires, exceeds, removes) with nothing between subject and verb. Rewrite (R3) an appositive or ", not Y," between them ("the estimator, a weighted correlator, returns"), a qualifier before the subject ("rounded to one sample, the lag is the estimate" becomes "the estimate is the lag, rounded to one sample"), a claim in a trailing relative clause ("renders one as the line that ``sensor-sweep`` logs"), or a light verb plus abstract noun ("has a requirement that ..."). Not a fix: moving the verb to a second clause on a pronoun that points back ("..., but coarse alignment fails it too"). Keep: a connective opener ("Thus,", "Further,", "First,") or a condition of about eight words or fewer.
    - **`attach`: one head per modifier, and next to it.** Test: each participle, relative clause, "to <verb>", or prepositional phrase has one word it can modify and sits beside it. Rewrite (R3) if two candidates exist, if a comma-bracketed clause separates it from its head, or if it narrates an event with its own time ("the capture analyzed when the cache filled" becomes "the capture under analysis", with the event in a sentence of its own). Rewrite (R9) an object relative clause that ends a clause on its verb ("the cache that `sw.spectrogram` reads" becomes "the cache read by `sw.spectrogram`"); the reader carries the noun until the verb arrives. No sentence or clause ends in a preposition ("the `Sweep` that the resources open for" becomes "the `Sweep` for which the hardware is opened"). A purpose infinitive follows its verb directly. Keep: a participle that states a property ("the gated estimate"); a subject relative clause ("the captures that follow the loop point"); an object relative clause followed by its own qualifier ("the captures that `sweep` runs, repeated by a leading `Repeat`").
    - **`join`: what a comma, a semicolon, and a colon may join.** Test: count the independent clauses (a finite verb with its own subject outside any that/which/when/because clause). Rewrite (R4, R5) a bare comma between two, a semicolon beside a conjunction, more than three, clauses that could be reordered without changing the argument (a list), or a colon in place of "because", "so", "which means", or "for example". A colon announces a specification, list, or restatement. A semicolon does not append a critique to a description. Several rules are a list, one "condition: what is set" per item, with no numbered narrative and no appositive after the consequence.
    - **`verdict`: no grade, filler, or opener without its number.** Test: delete each adjective, opener, and filler in turn; if no number, baseline, or condition is lost it stays deleted, and if one is implied, write it (R6). For a verb of change or degree, ask by how much or under what condition. The grades, antitheses, openers, praise, and boasts are in the table. "robust" takes an object ("robust to a DC offset") or is not written; a boast becomes the cost or nothing.
    - **`compare`: a comparison is a clause with a named baseline.** Test: the baseline, quantity, amount, and condition are all present, and the baseline does not trail the number as ", compared with <value>". Fix: R7 ("0.6x the numexpr time in float32 on the TX2i"), or the comparison is not made.
  - **Recipes.** R1 invert to the quantity: "<quantity> is limited by / set by / determined by <cause>". R2 demote the device to a condition: "With <device>, <quantity> fell within <value>". R3 move the fronted qualifier, the appositive, or ", not Y," after the main clause or into its own sentence, and make the relation verb the main verb. R4 split: one condition with its consequence per sentence, or one list item per rule. R5 replace the colon with "because", "so", "which means", or a period. R6 delete the word, or write the number, condition, or fact it stood for. R7 "Compared to <baseline>, <quantity> changes by <amount> under <condition>." R8 write the rule the outcome stands for: "<condition>: <quantity> takes <value>" ("a key set in several sources takes the value from the last source"). R9 write the relation of a code object to a noun as a participle after the noun ("the cache read by `sw.spectrogram`"), or as a clause with the function as subject ("`sw.spectrogram` reads the design from that cache").
  - **Mechanics.** Digits for counts ("3 statistics", "2 ports"); the Oxford comma; American spelling; "e.g.," and "i.e.," with the trailing comma.
  - **Not written.** Each is replaced by the condition, the number, the task, or nothing. The verbs a subject class may not take are in the `agent` table.

    | Group | Not written | Write instead |
    |---|---|---|
    | Person and narration | "I", "we", "our", "us", "you", "your", "let's"; "they", "their", "them" for a variable, attribute, capture, template, or quantity; "whose"; "first we ... then we ..."; "the following"; "this will"; a sentence addressed to a reader or writer ("you are editing", "once you commit") | the noun; "the captures with gain above" for "the captures whose gain exceeds"; a list for a sequence (`tests/test_docstrings.py` gates the pronouns and "whose" in `src/`) |
    | Placeholder nouns and renamings | "this behavior", "edge cases", "the result", "the logic", "various", "etc.", "as expected", "the right thing", "what it does", "the present context"; "this pipeline", "this chain", "this logic", "the machinery" for a thing already named | the condition the placeholder stands for; the noun of first mention |
    | Hedges and fillers | "should" where "must" is meant, "try to", "attempt", "safely", "properly", "simply", "just", "basically", "essentially", "effectively", "note that", "it is worth noting", "make sure", "sanity check", "for convenience", "under the hood" | the condition or the requirement |
    | Connective openers | "Additionally,", "Moreover,", "Furthermore,", "Importantly,", "In other words", "In order to" | "Further,", "Thus,"; the infinitive after its verb |
    | Grades, praise, and verdict openers | "proper", "genuine", "real", "true", "clean", "cheap" as a judgement, "circular", "one-sided"; "data, not assertions", "behavior rather than mechanism" as a slogan, "The problem is the cache."; "This is important", "X is a solved problem", "the key insight is", "X has a cost:", "the trade-off is", "the catch is"; robust (without an object), powerful, elegant, seamless, crucial, critical, comprehensive, clean, efficient, flexible, convenient, graceful, novel; "with speed optimizations" | the fact, the condition, or the shortfall with its number and consequence; the resource saved or the cost |
    | Time and change words | "now", "no longer", "previously", "new", "legacy", "used to", "fix", "workaround", "TODO", "for now" | the condition the code finds (**Present tense, present code** under Docstrings) |
    | Lexicon | "utilize", "towards", "in practice", "trivial", "crucial", "vital", "very" as praise, "ground truth" outside quotation marks | "use", "toward", the condition, "straightforward", "key", the number |
    | Idioms and effort estimates | "an afternoon's work", "low-hanging fruit", "should go", "a leftover", "earns its place", "going forward", "at the end of the day", "in the other direction" | the task, the deletion, or the number |
  - **Commit messages.** The summary line is one imperative clause of about 72 characters or fewer that names the effect of the change ("Wait for the source backend before the sink reads its power units"), with no trailing period and no tag prefix; a summary that names no effect ("cleanup", "tweaks", "misc fixes", "updates") is not written. The body, when the summary does not carry the whole fact, states the condition the change addresses and what the code does after it, in the present tense of the new code ("`lookup.power_units` waits on the id slot"), one fact per sentence. Not written: "this commit", "now", "also", a list of the files touched, a progress note, or a sentence about the session or the reviewer. A docstring or prose rewrite is its own commit, named as such (**Prose changes stay visible**). The `Co-Authored-By` trailer stays as the tooling writes it.
  - **Check.** One pass, after editing, over every comment, docstring, and commit message of the change: the test of each rule in the order listed, then the table; re-run `noun`, `agent`, and `verb-first` on any sentence a split creates. A sentence proposed by a reviewer, an agent, or a search-and-replace is new prose and gets the same pass in place; a rewrite applied from a list is how the habits above return. The pass covers the prose of the code the task has changed, not prose read along the way; a wider pass requires an explicit request from the user.

- **Comments:** only write one if a competent engineer or agent reading the code cold would be surprised or misled without it. Worth writing: a non-obvious *why* (constraint, workaround, domain rule, performance trade-off); something that looks wrong but is intentional; external context that can't be inferred from the code (section from a technical standard, peer-reviewed publication, government report, public documentation, upstream bug/issue number); an invariant or precondition the types don't enforce. Do not write:
  - changelog or progress notes (`# added null check`, `# refactored from previous version`) — the diff is already in git. Progress notes belong in the chat response, the commit message, or the PR description, never in a source file comment;
  - narration of the obvious (`# loop over captures`, `# return the result`);
  - restatements of the signature or type annotations;
  - conversational leakage (`# as requested`, `# per the instructions`, `# TODO: user said to`);
  - section banners, unless the file is genuinely huge. Note that the existing `# %% Capture specs` markers are Jupyter-style cell delimiters, not decoration.

  If a comment is needed to explain *what* code does, prefer renaming or extracting a function instead — that removes the cause rather than the symptom. Comments are for *why*. A comment takes the function or the value as subject and states or cites the constraint, standard, or issue; it is checked once under **Check**.

- **Docstrings** are the API reference (mkdocstrings renders them into the zensical site from `docs/api/`), so write them as the caller's contract: inputs, outputs, side effects, exceptions. Google sections only — `Args:`, `Returns:`, `Yields:`, `Raises:`, `Examples:`, `References:` — never `Arguments:`, numpy underlines, or ad hoc headers. Compose each part from its template and run **Check** once on the finished docstring.
  - **Templates.** Each part states what the signature cannot: units (Hz, s, S/s, dB vs linear power), shape and which axis holds what, dtype, dimension names, dict keys, valid range or ratio constraint, and what `None`, `inf`, or `'auto'` selects. `x: input array` and `fs: sampling rate` are omissions, not entries.

    | Part | Template |
    |---|---|
    | Summary line | `<imperative verb> the <effect or quantity> (<units>) <of/for/at> <input>.` ("return the duration (in s) of one 3GPP slot at `subcarrier_spacing`."); lowercase first word; one claim; the period is dropped only when the whole docstring is one line |
    | `Args:` entry | `<name>: <what the value selects, constrains, or shapes>, <unit, shape, dtype, or range>; <None/inf/'auto'> <selects what>`; 1 clause, at most 2 |
    | `Returns:` | `<shape or dimension names>, <units>, <dict keys>; the array namespace follows <input>` |
    | `Yields:` | `<item>, <units>; iteration ends when <condition>` (`loop=True` is infinite) |
    | `Raises:` | `<Exception>: <condition>`, for every exception the caller can act on; never one that only a bug raises, never the message text |
    | Side effects | one prose sentence per effect: in-place modification (`overwrite_x`, `out=`, including an `out=` that is accepted but not honored), process-global state (logger handlers, caches, the GPU lock), threads started, files written |
    | Log mention | "logs on `<logger>` at `<LEVEL>` when <condition>"; never the message text |
    | Attribute docstring (dataclass field, class attribute) | a string literal on the line after the field: one noun phrase with units and range, and what `None`, `inf`, or `'auto'` selects (`snr_dB: float` then `"""peak SNR (dB) above the calibrated noise power"""`); the `Args:` entry rules apply |
    | Class | what an instance is, what construction requires, and the state or lifecycle the methods share (a context manager); at most 3 sentences; no sentence about one member or one field |
    | `__init__` | what is stored, and what is opened or derived ("store `spec`; nothing is opened or derived.") |
    | Module | the theme in one sentence, and one implementation fact that applies across the module and is written in no comment |
    | Coordinate factory (`@registry.coordinates`) | one noun phrase: what the values index, with origin, step, span, and the fields that set them (`"""time from the start of the capture, in steps of \`detector_period\`"""`) |
    | Measurement (`@registry.measurement`) | prose on the values the `Output:` list does not render (normalization, `nan` entries, what a bin collects); then `Output:` (under **Measurement docstrings**), `Raises:`, `References:`, and `Args:` with `{args}` last |
  - **What a docstring says.** The object's own contract: what it requires, returns, raises, and changes. Not what other code does with the object (where a function is registered, which caller invokes a method, when another class reads an attribute: "registered as the `on_cached` callback", "`iterate_sweep` calls `iterate`"); a hook may name its intended consumer in one clause of its own docstring ("the sink entered by `open_resources`") and no more. Not the mechanism: a method is named only when it decides the result or the cost (overlap-add edge behavior, the copy made by `_truncated_buffer`, a disk-cached window design), and the steps of the body are stated only when they are the observable precedence (`loop_captures`), as rules. Not the reason for a constraint, which belongs in a comment at the line that enforces it. Not the code of the return value, but the inputs it is computed from and its bounds. A docstring that narrates mechanism, names a `.lib` module, or describes the change that produced it costs review time and returns nothing: when a refactor touches a documented object, delete the sentences about the old mechanism rather than rewriting them, and add a sentence only for a caller-facing rule (what a value selects, what is rejected, which input a derived value comes from). A summary line alone is a complete docstring.
  - **Entries before prose.** A fact about one parameter is that parameter's `Args:` entry, and a fact about the return value is the `Returns:` entry; the prose above the sections carries only facts that span several parameters or the object's state. Three sentences that each name one parameter are an `Args:` block written in the wrong place. An entry says how the value selects, constrains, or shapes the output, not what the body does with it ("the implementation invokes ...", "the calibration path and the source id are read"); a behavior the body applies to one argument is a prose sentence when this function owns the behavior, and one prose sentence naming the owning function when another function does ("An implementation runs `iterate_captures` over `resources`."). A sentence that restates an entry, or that points the reader to another object's docstring ("whose docstring describes the yields"), is deleted: the docstring stands on its own, and autodoc links the names in backticks.
  - **Summary line.** `pixi run -e test39 ruff check --select D401 src` lists non-imperative summaries ("an iterator that ...", "helper for ...", "designs ..."); it is not enforced, so run it on files you touch. One claim per line: a trailing participial clause is cut into its section (", yielding what the sink's `append` returns" becomes a `Yields:` entry; ", raising what the builder raises" a `Raises:` entry). "run the action over `resources`." is a whole summary. A coordinate factory docstring is the one exception to the imperative summary, so `D401` flags it by design.
  - **Module docstrings.** Do not catalog the module's contents or repeat details of the objects in its namespace; autodoc renders those from the objects' own docstrings. No return types, signatures, or naming patterns of the members (`describe_*`); no statement of what the module does not do ("nothing here logs"); no reference to the program that consumes the output.
  - **Class and attribute docstrings.** Every fact about one method, property, or field goes in that member's docstring; a class docstring sentence that names one field is an attribute docstring written in the wrong place. For a `Protocol`, the class docstring states the role an implementation plays and nothing about registration, callers, or inheritance. Spec-struct fields are documented through `Meta`, and the spec class docstring says how the fields interact. Do not write an `Attributes:` section: mkdocstrings lists the documented attributes itself. An `__init__` docstring is merged into the class page (`merge_init_into_class`).
  - **Predicate nouns.** In every "X of Y" and "Y's X", Y is the thing that has X. "The IM3 victims of a port" fails: the products belong to the signal of the capture at that port, and the victims are the frequencies those products fall on. Rewrite until each possessive names the actual owner.
  - **Present tense, present code.** Nothing about what the code used to do, was changed to do, or may do later; the time and change words are in the **Not written** table. Code that converts older data describes the condition it finds ("`units` of the form `dBm/<bandwidth>`"), not the version or era that wrote it ("stores written before X carried Y").
  - **Cite external context.** A standard section, a paper, or an upstream issue is cited in its short form inline, in parentheses ("(3GPP TS 38.211 §5.3.1)", "(Gardner 1986)"). The long form of each citation (full title, authors or standards body, year, URL or DOI) goes under a `References:` section at the end of the docstring, one entry per source.
  - **Do not duplicate what the tooling injects.** Spec-struct fields are documented through `Meta(description=..., units)`; the class docstring says what the block configures and how its fields interact, never a field list. A measurement docstring ends with `Args:\n    {args}`, which the registry fills from the `Meta` field metadata of `spec_type`, so every field is already documented there; the prose above repeats none of that content. Read the field metadata first to find the context the prose still has to supply: the output values (dtype, units, normalization), how the fields interact, and the conditioning the measurement registers. `Controller` subclass and `arm` docstrings are generated. The griffe extension `docs/griffe_striqt.py` substitutes the filled measurement docstrings and the `Meta` field descriptions into the static model when zensical renders the API reference.
  - **Measurement docstrings.** A function decorated with `@registry.measurement` carries an `Output:` section between the prose and the remaining sections, written as this bullet list with the placeholders verbatim (the registry fills `{dtype}`, `{dims}`, `{coords}`, and `{attrs}` at registration, and mkdocstrings renders the section as an admonition):

    ```
        Output:
            - Array dtype: {dtype}
            - Dimensions: {dims}
            - Coordinates: {coords}
            - Attributes: {attrs}
              * `noise_bandwidth`: the bandwidth (in Hz) that the values are referred to
    ```

    `{dtype}` renders as the registered dtype name. `{dims}` renders as the backticked dimension names of the returned `DataArray`, `port` first. `{coords}` renders a nested list with one ``* `name` (dtype, units): description`` item per entry of `coord_factories`, from the registration and the docstring of the factory; a measurement registered without coordinate factories omits the `Coordinates` bullet. `{attrs}` renders a nested list of the registered attrs other than `standard_name` and `long_name` (`units`, when registered). The attrs that the measurement body returns (`units` when the body sets it, `noise_bandwidth`, `resolution_bandwidth`) are hand-written items on the lines after `{attrs}`, indented 2 spaces under the `-`, one ``* `key`: value`` item per attr, with units and the fields the value comes from; a `units` item states only that the power units follow the acquisition and what the unit is when calibrated ("power units based on acquisition (dBm when calibrated)"). A measurement with no registered `units` and no body attrs omits the `Attributes` bullet. Section order is prose, `Output:`, `Raises:`, `References:`, then `Args:` with `{args}` last. The prose above the sections names no dimension, no coordinate, and no attr: a fact about one coordinate is the docstring of that coordinate factory, a fact about one attr is an `Attributes` item, and the prose repeats nothing the list renders (dtype, dimensions, units, the attrs). A fact about the values that the list does not render (normalization, `nan` entries, what a bin collects) stays in the prose.
  - **Coordinate factory docstrings.** The docstring of a function decorated with `@registry.coordinates` is the attribute docstring of the coordinate, not a description of the factory. The registry renders the first paragraph as the coordinate entry in every `{coords}` list that includes the factory, after the registered dtype and units, so the phrase repeats neither. Further paragraphs (a `Returns:` for the attrs the factory returns) are not rendered in `{coords}`. A factory without a docstring renders as its `standard_name`; `tests/analysis/test_analysis_register.py` requires a docstring on every registered factory.
  - **Markup.** Identifiers in single backticks (they render italic: no `default_role`), literal code in double backticks, examples in doctest form (ruff formats them with `docstring-code-format`).
  - **Length follows audience.** Public API (`striqt.analysis`, `striqt.sensor`, the `waveform` shims) gets full sections; a private `.lib` helper gets a summary line plus only the sections that carry information. No docstring beats one that restates the name.
  - **Scope of a change.** Bring the docstring of any function you edit to this standard, including stale parameter names and exception lists. Do not rewrite docstrings of untouched functions in the same change. A revision pass over docstrings or comments covers only the code the task has changed, never code read along the way; a wider pass requires an explicit request or authorization from the user.
  - **Prose changes stay visible.** A docstring rewrite goes in a commit whose message names it, never inside one titled for a rename or refactor. The final chat message of a change lists every docstring touched, by qualified name, so the list can be reviewed without the diff.
  - **Gate.** `tests/test_docstrings.py` fails on any docstring under `src/` that contains a `striqt.<pkg>.lib` path outside a `lib/` directory, or one of "we", "our", "you", "your", "they", "their", "them", or "whose" outside backticks and doctest lines ("I" and "us" are not scanned: "I/Q" and the microsecond abbreviation). The scan has no baseline: every docstring under `src/` must pass.

## Testing

The map of the test suite (where things are tested, which module owns shared setup, the tolerance models, backend fixtures, pytest extensions, the xfail ledger, and how to verify a test change) is `tests/AGENTS.md`; read that file before working under `tests/`. The judgement calls (what to assert, when a test is redundant, how to record a defect) are in the `writing-tests` skill, which is not tracked in the repository.

## Status

Early beta. Base-package APIs are expected to be stable; `.lib` internals, YAML schemas, and CLI options may still shift. The sweep schema is the set of spec structs under `striqt.sensor.specs` (`sa.specs.helpers.json_schema` renders it as JSON schema). `tests/sensor/sweeps/synthetic.yaml`, `tests/sensor/sweeps/site/*.yaml` and `tests/sensor/sweeps/fake_soapy-*.yaml` are the most current worked examples.
